bpf, riscv: Support Exceptions

https://lore.kernel.org/all/20240201125225.72796-1-puranjay12@gmail.com/

Kumar 正在为 BPF 添加异常支持，并在 x86 上启用 [1]。
我正在与他合作，在 ARM64 上启用该功能，并将在基本的异常支持合并到上游后，继续在其他架构上实现。

[1] https://lore.kernel.org/bpf/20230912233214.1518551-1-memxor@gmail.com/

为 ARM64 的 JIT 实现 `arch_bpf_stack_walk()`。这将被 `bpf_throw()` 用于展开栈，直到标记为异常边界（exception boundary）的程序，并使用主程序的栈运行回调函数。

程序的 prologue（序言代码）生成部分已被修改，使得回调程序能够使用标记为异常边界的程序的栈，在此栈中已压入了被调用者保存的寄存器（callee-saved registers）。

由于 `bpf_throw` 函数不会返回，如果它破坏了任何被调用者保存的寄存器，则这些寄存器会一直保持被破坏的状态。因此，异常边界程序的 prologue 被修改为同时压入 R23 和 R24 寄存器，而回调函数将在其 epilogue（尾声代码）中恢复它们。

《Arm 64 位架构的过程调用标准》[1] 指出，寄存器 r19 到 r28 应由被调用者保存。ARM64 上的 BPF 程序已经保存了所有被调用者保存的寄存器，除了 r23 和 r24。此补丁在程序的 prologue 中添加了一条指令以保存这两个寄存器，并在 epilogue 中添加了一条指令以恢复它们。

只有在使用 `bpf_throw()` 时才会添加这些额外的指令。否则，发出的 prologue/epilogue 将保持不变。

[1] https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst

unwind, riscv: add sframe unwinder for kernel

https://lore.kernel.org/live-patching/20250127213310.2496133-1-wnliu@google.com/

本补丁集实现了一个基于 sframe 的通用内核栈展开器（unwinder）。主要目标是为 arm64 提供可靠的堆栈跟踪功能。

在 x86 架构上，orc 栈展开器能够提供可靠的堆栈跟踪。但在 arm64 上，objtool 缺乏必要的支持，无法生成适用于 arm64 的 orc 展开表。

目前，已经有一个针对用户空间的 sframe 栈展开器提案 [2]。由于 sframe 展开表的算法类似，这两个提案在未来可以整合共同的功能。

当前仍存在一些不完整功能或挑战：
- 当前的展开器还不能处理内核模块。来自内核模块的 FRE 的 `start_addr` 显示不正确，导致我们无法展开内核模块中的函数。
- 目前只有 GCC 支持 sframe。

参考资料：
[1]: https://sourceware.org/binutils/docs/sframe-spec.html  
[2]: https://lore.kernel.org/lkml/cover.1730150953.git.jpoimboe@kernel.org/

Support of Virtual CPU Hotplug for ARMv8 Arch

https://lore.kernel.org/all/20241015100012.254223-1-salil.mehta@huawei.com/

# 概要
============
本补丁集为 QEMU 中的 ARMv8 架构引入了虚拟 CPU 热插拔支持。其理念是在不重启 guest VM 的情况下，能够动态地热插拔和热移除 vCPUs。此功能*并不*假设主机系统中物理 CPU 热插拔的可用性，而是尝试在虚拟化层/QEMU 层解决该问题。它引入了 ACPI CPU 热插拔钩子和事件处理机制，以与 guest 内核进行接口，并添加了初始化、插入和移除 CPU 的代码。除了用户空间/Qemu 中对 hypercall 退出处理的支持（最近已加入内核）外，不需要对主机内核/KVM 进行任何更改。James Morse (ARM) 在邮件列表中发布了相应的 guest 内核更改 [3] [4]，这些更改最近已被接受并已成为 v6.11 主线内核的一部分。

## 动机
================
这使得可以按需扩展 guest VM 的计算能力，在以下示例场景中有用：
1. 云中的垂直 Pod 自动扩展 [9][10]：作为编排框架的一部分，可以根据使用情况调整 pod 中容器的资源请求（CPU 和内存请求）。
2. 按需增长业务模型：基础设施提供商可根据 SLA（服务等级协议）分配并限制 guest VM 可用的总计算资源数量。VM 所有者可付费请求更多计算资源进行热插拔。

例如，Kata Container VM 一开始只分配最小量的资源（即采用热插拔一切的方式）。原因？
1. 允许更快的 *启动时间*
2. 减少 *内存占用*

Kata Container VM 可以仅用 1 个 vCPU 启动，之后根据需要再热插拔更多的 vCPU。一般来说，减少 VM 中的 vCPU 数量可以在核心数增加时显著减少 VM 的启动时间。

**[即将推出]**
我正在利用此补丁集中提出的热插拔基础设施来增强 ARM/VM 的启动时间。敬请期待接下来的补丁，它们将利用此基础设施显著减少 *非热插拔* 场景下的启动时间。预计在接下来的几周内发布更新！

## 术语
================
(*) 可能的 CPUs：VM 中可能存在的最大 vCPU 数量。包括任何冷启动的 CPUs 以及之后可以热插拔的 CPUs。
                   - Qemu 参数 (-smp maxcpus=N)
(*) 当前的 CPUs：ACPI 标记为 'present' 的可能 CPUs。这些可能或未被标记为 ACPI 'enabled'。
                   - 当前的 vCPUs = 可能的 vCPUs（在 ARM 架构上始终如此）
(*) 已启用的 CPUs：ACPI 标记为 'present' 和 'enabled' 的可能 CPUs，现在可以被 Guest Kernel 使用（PSCI 上线）。
                   - Qemu 参数 (-smp cpus=N)。可用于指定 VM 初始化期间的一些冷启动 vCPUs。也可以通过 '-device' 选项添加一些。

## 由于 ARMv8 CPU 架构的限制 [+] 其他障碍
===================================================================
A. 物理层面支持 CPU 热插拔的限制：（架构约束）
   1. ARMv8 CPU 架构不支持物理 CPU 热插拔的概念。
      a. 存在许多每个 CPU 组件（如 PMU、SVE、MTE、架构定时器等），当 CPU 被热插拔时，其行为需要明确定义。对此没有规范。
   2. 其他 ARM 组件（如 GIC 等）目前也未设计用于实现物理 CPU 热插拔功能。例如，
      a. 每个物理 CPU 都有一个唯一的 GICC（GIC CPU 接口）。架构并未规定 CPU 热插拔在此类组件上下文中的含义。
      b. CPU/GICC 实际上是连接到唯一的 GICR（GIC 分发器）的。GIC 分发器始终属于始终开启的电源域。因此，根据规范，它们无法被关闭。
B. 固件/ACPI 中的障碍（架构约束）
   1. 固件必须向 OS 暴露 GICC、GICR 和其他每 CPU 功能（如 PMU、SVE、MTE、架构定时器等）。由于第 A1(a) 节所述的架构约束，所有描述 GIC CPU 接口和 GIC 分发器的 MADT 中断控制器结构必须在启动时由固件提供给 OSPM。
   2. 支持 CPU 热插拔的架构可以通过评估 ACPI _MAT 方法在启动后从固件获取此类信息，并且 OSPM 具备处理这些信息的能力。ARM 内核使用 MADT 中中断控制器结构中的信息在启动时识别当前的 CPU 数量，因此不允许在启动后更改这些信息。当前的 CPU 数量不能更改。这是一个架构约束！
C. KVM 支持虚拟 CPU 热插拔的障碍（架构约束）
   1. KVM VGIC:
      a. 与重分发器相关的各种 VGIC 资源（如内存区域等）的大小仅在 VM 初始化时一次性确定，之后无法更改。
         KVM 基于 vCPU 的数量和重分发器范围的数量/大小静态配置这些资源。
      b. vCPU 与其 VGIC 重分发器之间的关联在 VM 初始化时固定在 KVM 中，即当重分发器 iodevs 注册时。VGIC 不允许在 VM 初始化之后设置或更改这种关联。物理上，每个 CPU/GICC 都与它的重分发器唯一连接，并且没有架构上的方法可以设置这一点。
   2. KVM vCPUs:
      a. 缺乏规范意味着 KVM vCPUs 的销毁不存在，因为没有参考说明如何处理其他每 vCPU 组件（如重分发器、架构定时器等）。
      b. 实际上，KVM 并未为任何架构实现 vCPUs 的销毁。这与架构是否实际支持 CPU 热插拔无关。例如，即使是 x86 KVM 也不实现 vCPUs 的销毁。
D. Qemu 支持虚拟 CPU 热插拔的障碍（KVM 约束->架构）
   1. 必须创建 Qemu CPU 对象以初始化所有 Host KVM vCPUs，以克服 KVM 约束。KVM vCPUs 是在 Qemu CPU 对象实现时创建和初始化的。但是，为“尚未插入”的 vCPUs 保留 QOM CPU 对象可能会在使用 device_add 插入新 vCPUs 并创建新的 QOM CPU 对象时引发问题。
   2. GICV3State 和 GICV3CPUState 对象必须在 VM 初始化时基于 *可能的 vCPUs* 大小进行配置，此时 QOM GICV3 对象实现。这是因为 KVM VGIC 只能在初始化时一次性初始化。但每个 GICV3CPUState 都有一个关联的 QOM CPU 对象。之后可能对应的是“尚未插入”（初始化时未插入）的 vCPUs。
   3. 如何将新的 QOM CPU 对象重新连接回 GICV3CPUState 对象，并在 CPU 被热插拔时断开连接？
   4. 如何在 QOM 中表示“未插入”或“尚未插入”的 vCPUs？对于已经存在 KVM vCPU 的情况，例如是否保留：
       a. 没有 QOM CPU 对象 或
       b. 未实现的 CPU 对象
   5. 如何通过 ACPI 将 vCPU 状态暴露给 Guest？尤其是那些在 QOM 中可能不存在的“未插入”或“尚未插入”的 vCPUs，而 Guest 总是期望所有可能的 vCPUs 在启动时都被标识为 ACPI *present*。
   6. 如何通过 ACPI MADT 表向 Guest 暴露 GIC CPU 接口，针对“未插入”或“尚未插入”的 vCPUs？
E. 方法总结 ([+] A, B, C & D 节中问题的变通方案)
   1. 在 VM 初始化时，预先创建所有可能的 Host KVM vCPUs，即使这些 vCPUs 尚未在 Qemu 中插入，也保持它们处于关机状态。
   2. 在 Host 中初始化 KVM vCPUs 之后，对应于“未插入”或“尚未插入”的 vCPUs 的 KVM vCPU 对象会被挂起到现有的 per-VM "kvm_parked_vcpus" 列表中。（类似 x86）
   3. GICV3State 和 GICV3CPUState 对象在 VM 初始化时基于可能的 vCPUs 进行配置，即当 Qemu GIC 实现时。这反过来会基于可能的 KVM vCPUs 数量调整 KVM VGIC 资源（如内存区域等）的大小。VM 初始化后，这一数值不会改变。
   4. 对应于“未插入”或“尚未插入”的 vCPUs 的 Qemu CPU 对象在 Host KVM CPU 和 GIC/VGIC 初始化后释放。
   5. 构建 ACPI MADT 表时包含以下更新：
      a. GIC CPU 接口条目数量 (=可能的 vCPUs)
      b. 将启动 vCPU 标记为 MADT.GICC.Enabled=1（不可热插拔）
      c. 将可热插拔的 vCPUs 标记为 MADT.GICC.online-capable=1  
         - MADT.GICC.Enabled=0（互斥）[6][7]
	 - Guest 启动后可通过 ACPI 启用+上线 vCPU（固件策略）
	 - 与上述相关的问题（详情见后续章节）
   6. 向 Guest 内核暴露以下 ACPI 状态：
      a. Always _STA.Present=1（所有可能的 vCPUs）
      b. _STA.Enabled=1（已插入的 vCPUs）
      c. _STA.Enabled=0（未插入的 vCPUs）
   7. vCPU 热插拔 *实现* 新的 QOM CPU 对象。以下会发生：
      a. 实现、初始化 QOM CPU 对象并生成 Qemu vCPU 线程。
      b. 从现有的 "kvm_parked_vcpus" 列表中取消挂起 KVM vCPU。
         - 附加到 QOM CPU 对象。
      c. 在 Host 中重新初始化 KVM vCPU。
         - 重置核心和系统寄存器，设置默认值等。
      d. 运行 KVM vCPU（使用 "start-powered-off" 创建）。
	 - vCPU 线程休眠（等待通过 PSCI 的 vCPU 重置）。
      e. 更新 Qemu GIC。
         - 重新连接与此 vCPU 相关的 IRQ。
         - GICV3CPUState 与 QOM CPU 对象的关联。
      f. 更新 [6] ACPI _STA.Enabled=1。
      g. 通知 Guest 新的 vCPU（通过 ACPI GED 接口）。
	 - Guest 检查 _STA.Enabled=1。
	 - Guest 添加处理器（向 LDM 注册 CPU）[3]。
      h. 在插槽中插入 QOM CPU 对象。
         - slot-number = cpu-index {socket, cluster, core, thread}。
      i. Guest 上线 vCPU（通过 HVC/SMC 的 CPU_ON PSCI 调用）。
         - KVM 退出 HVC/SMC Hypercall [5] 到 Qemu（策略检查）。
         - Qemu 在 Host 中启动 KVM vCPU。
   8. vCPU 热移除 *取消实现* QOM CPU 对象。以下会发生：
      a. 通过 ACPI GED 接口通知 Guest vCPU 热移除事件。
         - Guest 下线 vCPU（通过 HVC/SMC 的 CPU_OFF PSCI 调用）。
      b. KVM 退出 HVC/SMC Hypercall [5] 到 Qemu（策略检查）。
         - Qemu 在 Host 中关闭 KVM vCPU。
      c. Guest 向 Qemu 发送 *弹出* vCPU 的信号。
      d. Qemu 更新 [6] ACPI _STA.Enabled=0。
      e. 更新 GIC。
         - 断开与此 vCPU 相关的 IRQ。
         - GICV3CPUState 与新的 QOM CPU 对象的关联得到更新。
      f. 移除 vCPU。
	 - 从插槽中移除。
         - 挂起 KVM vCPU ("kvm_parked_vcpus" 列表)。
         - 取消实现 QOM CPU 对象并合并 Qemu vCPU 线程。
	 - 销毁 QOM CPU 对象。
      g. Guest 检查 ACPI _STA.Enabled=0。
         - 移除处理器（从 LDM 注销 CPU）[3]。
