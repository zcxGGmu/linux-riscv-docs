Design doctrine
为什么不是单模型串到底
探索 -> 规划 -> 生成 -> 审核 -> 调试 -> patch-ready

规则:
1. 全流程工件化
2. 生成/审核允许多轮
3. Debug 不得直接放行
4. 所有外部写操作前必须人工 Gate
内核上下文高度依赖历史与架构语义
实现者自审会放大遗漏风险
把失败拆给 Failure-Analyzer / Fix-Agent 更利于归因
并行审核比“实现者复读”更稳

Demo Issue：riscv/kvm MMU Kconfig 一致性修复

Issue
Round 1
Debug
Round 2
目标：让 dependency/help text 都显式表达 MMU 约束
范围：只触及 arch/riscv/kvm/Kconfig
风险：低，但属于 Kconfig 用户可见变化
实现通过模拟构建检查
但 Spec Review 指出 help text 未闭环
结论：ENTER_DEBUG
Failure-Analyzer 认定为 spec gap
Fix-Agent 继续单文件修复
保持单 patch、可回滚
补充 help text 的 MMU 说明
Spec Review Round 2: PASS
状态流转到 patch-ready
这个 demo 证明：审查失败并不一定意味着代码坏了，也可能只是“实现没有完整满足设计目标”。

技术评审结论

这套方案为什么可行
仍需谨慎的地方
建议决策
职责解耦：探索、规划、实现、审核、调试分层
状态显式：所有阶段都回写 workflow.yaml 与工件目录
闭环可控：round 上限 + 人工 Gate + patch-ready 定义
架构语义争议
真实 lore 证据补齐
日志真实性与回归覆盖
发信礼仪与 maintainer 偏好
先用 MVP 跑一个高置信度窄 issue
强制经历至少 2 轮生成/审核
把真实工具链日志接入现有工件目录

不是“多开模型”，而是“多角色互相制衡”
