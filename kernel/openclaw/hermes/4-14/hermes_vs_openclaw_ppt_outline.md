# Hermes vs OpenClaw：PPT 提纲版

> 适用场景：向老板、架构委员会、研发负责人做 8~10 页的正式汇报。
> 目标：说明为什么在 AI 辅助 Linux 内核 / 驱动 / BSP 开发场景中，Hermes 相对 OpenClaw 更有优势。

## 封面页

标题：
Hermes vs OpenClaw：AI 辅助内核开发能力对比

副标题：
为什么“工程执行型 Agent”更适合 Linux 内核 / 驱动 / BSP 团队

页内要点：
- 汇报对象：管理层 / 技术负责人
- 汇报目标：选型判断与能力定位
- 汇报结论：Hermes 更适合作为内核研发辅助 Agent

备注：
封面可用“代码仓 + 终端 + 构建日志”视觉，而不是聊天气泡风格。

## 第 1 页：执行摘要

标题：
一句话结论

建议文案：
- OpenClaw 更强于“多渠道、长期在线、产品化个人 AI 助手平台”
- Hermes 更强于“进入代码仓、本地工具链和研发闭环的工程型 Agent”
- 在 AI 辅助 Linux 内核 / BSP 开发场景里，Hermes 更直接提升生产力

页面布局建议：
- 左侧放 OpenClaw 定位
- 右侧放 Hermes 定位
- 底部放一句最终结论

## 第 2 页：先定义我们要解决的问题

标题：
内核研发真正需要 AI 做什么？

建议文案：
- 不是只做问答，而是进入真实研发现场
- 典型闭环：查问题 → 改代码 → 跑构建 → 看日志 → 写说明
- 场景对象：kernel / driver / DTS / Kconfig / Makefile / boot log / dmesg

可放的 6 个关键词：
- 搜索
- patch
- 编译
- 日志
- 分析
- 沉淀

核心结论：
在这个场景里，“执行”比“触达”更重要。

## 第 3 页：两者产品定位差异

标题：
OpenClaw 与 Hermes 的设计中心不同

左栏：OpenClaw
- personal AI assistant
- local-first gateway
- multi-channel inbox
- voice / canvas / companion apps
- 多代理路由、多入口接入

右栏：Hermes
- CLI Agent
- 文件读写与 patch
- 终端执行
- 子代理问题拆解
- 技能与记忆沉淀

收束结论：
OpenClaw 解决“助手在哪用”；Hermes 解决“助手怎么真正参与研发”。

## 第 4 页：为什么 Hermes 更适合内核开发

标题：
Hermes 的 4 个核心优势

建议拆成 4 个卡片：

1. 更贴近源码树
- 就地搜索、阅读、修改文件

2. 更贴近构建系统
- 可直接调用 shell / 编译 / 脚本 / 验证命令

3. 更适合复杂问题拆解
- 子代理并行分析 crash、probe、性能回退

4. 更利于长期知识沉淀
- 技能、记忆、文档一体化保留

页尾总结：
Hermes 不是把 AI 放在聊天入口，而是把 AI 放在工程闭环里。

## 第 5 页：对内核/BSP 的典型价值场景

标题：
Hermes 在哪些低层场景更有价值？

建议列 5 个场景：
- 驱动 probe 失败定位
- DTS 与驱动不匹配分析
- 交叉编译/链接错误处理
- 性能回退分析
- 上游提交流程辅助

每个场景一句描述：
- 能查定义、看日志、改 patch、补文档、沉淀流程

页面形式建议：
2x3 卡片式布局，最后一个格子放“更多场景：bring-up / suspend-resume / PM / clock / regulator”。

## 第 6 页：表格化对比

标题：
分维度对比：谁更适合内核研发？

建议放 6 行核心维度：

| 维度 | Hermes | OpenClaw | 更适合内核开发 |
|---|---|---|---|
| 产品中心 | 工程执行 Agent | 多渠道助手平台 | Hermes |
| 源码树就地作业 | 强 | 非核心主叙事 | Hermes |
| 构建/验证闭环 | 强 | 非主卖点中心 | Hermes |
| 文件精细 patch | 强 | 平台能力导向更强 | Hermes |
| 多渠道接入 | 一般 | 极强 | OpenClaw |
| 语音/移动端/Canvas | 非重点 | 很强 | OpenClaw |

讲解重点：
- 对个人助手场景，OpenClaw 很强
- 对低层研发场景，Hermes 更关键

## 第 7 页：管理层最该关注的价值

标题：
为什么这不只是工具差异，而是效率模型差异

建议文案：
Hermes 的价值主要来自 3 点：

1. 降低工程执行摩擦
- AI 直接参与仓库、构建、日志和文档

2. 缩短复杂问题定位时间
- 适合处理跨 DTS、driver、Kconfig、日志的联动问题

3. 形成团队长期复利
- 把个人经验沉淀成可复用工作流

建议放一个“短期 / 中期 / 长期”三段式：
- 短期：提效
- 中期：降错
- 长期：沉淀知识资产

## 第 8 页：适用边界与公平结论

标题：
什么时候选 OpenClaw，什么时候选 Hermes

左侧：更适合 OpenClaw
- 需要多渠道助手
- 需要长期在线
- 需要移动端/语音/Canvas
- 目标是 assistant platform

右侧：更适合 Hermes
- 目标是 Linux 内核 / 驱动 / BSP 团队提效
- 需要 AI 深入研发执行链路
- 需要沉淀调试套路和项目约定
- 目标是 engineering agent

## 第 9 页：最终结论页

标题：
最终建议

建议文案：
- 如果公司要建设“多入口个人 AI 助手平台”，OpenClaw 是强参考
- 如果公司要提升“AI 辅助内核研发”的真实产出，Hermes 路线更优
- 对 Linux 内核 / BSP 场景，优先选择工程执行型 Agent

可直接口播的最后一句：
OpenClaw 更像“把 AI 放到很多地方去用”，Hermes 更像“把 AI 放进研发现场里干活”。对内核开发，后者更重要。
