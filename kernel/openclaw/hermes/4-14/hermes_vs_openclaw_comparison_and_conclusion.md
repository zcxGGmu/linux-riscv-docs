# Hermes vs OpenClaw：表格对比 + 结论页 汇报材料版

> 用途：可直接复制到汇报文档或 PPT 中，适合作为“核心对比页 + 结论页”。

## 第 1 页：核心表格对比

标题：
Hermes vs OpenClaw：AI 辅助内核开发能力对比

副标题：
聚焦 Linux 内核 / 驱动 / BSP 研发场景，而非泛化个人助手场景

### 核心对比表

| 对比维度 | Hermes | OpenClaw | 对 AI 辅助内核开发的意义 |
|---|---|---|---|
| 产品设计中心 | 工程执行型 CLI Agent | 多渠道个人 AI 助手平台 | 内核研发更依赖前者 |
| 主要交互面 | 终端、源码树、文件、子代理 | Gateway、消息渠道、语音、Canvas | 内核研发主要发生在源码树和 shell 中 |
| 源码树就地作业 | 强，适合直接读写/patch 仓库内容 | 平台能力强，但公开定位不以源码作业为核心 | Hermes 更贴近开发现场 |
| 文件细粒度操作 | 强，适合局部 patch 和分段阅读 | 平台导向更强 | 低层代码库非常需要细粒度操作 |
| 构建与验证闭环 | 强，可直接配合终端与验证动作 | 不是公开主卖点中心 | 编译/日志/修复闭环决定真实生产力 |
| 复杂问题拆解 | 强，可做多子任务并行分析 | 有多代理能力，但更偏路由与隔离 | 内核问题通常跨 DTS/driver/Kconfig/log |
| 技能与知识沉淀 | 强，便于沉淀调试套路与团队流程 | 有 skills，但平台属性更强 | Hermes 更适合形成团队经验库 |
| 持久记忆 | 强，可绑定项目约定和用户偏好 | 有会话/工作区能力 | 长周期维护项目更受益 |
| 文档/补丁/实现一体化 | 强，可直接生成说明与落盘 | 可支持，但非主叙事重点 | 内核团队常需同时交付代码和说明 |
| 多渠道接入 | 不是核心优势 | 极强 | 这对个人助手价值更大 |
| 语音/移动端/Canvas | 非重点 | 很强 | 对内核研发帮助次一级 |
| 个人助手产品完成度 | 较强但非主路线 | 极强 | OpenClaw 在平台化方面明显更强 |

### 页尾结论（一句话）

如果目标是“让 AI 真正进入 Linux 内核 / BSP 的研发闭环”，Hermes 的能力组合更匹配；
如果目标是“建设一个多渠道、长期在线的个人 AI 助手平台”，OpenClaw 更占优。

## 第 2 页：结论页

标题：
最终结论与选型建议

### 结论

OpenClaw 和 Hermes 并不是同一种优化目标：

- OpenClaw 更擅长“把 AI 助手部署到很多渠道和终端上”
- Hermes 更擅长“让 AI 直接参与代码、构建、验证和文档沉淀”

如果问题严格限定为“AI 辅助内核开发”，Hermes 的相对优势更清晰。

### 为什么 Hermes 更适合内核/BSP 团队

1. 更贴近源码树和 shell
2. 更适合局部 patch 和细粒度修改
3. 更容易打通查-改-编-测-记闭环
4. 更适合拆解复杂低层问题
5. 更适合沉淀项目知识和团队流程

### 什么时候选 Hermes

- 要服务 Linux 内核 / 驱动 / BSP 团队
- 要让 AI 深入参与研发执行而不仅是问答
- 要沉淀调试套路、构建命令和项目约定
- 要降低复杂问题定位与回归成本

### 什么时候选 OpenClaw

- 要建设多渠道个人/企业 AI 助手平台
- 要覆盖 Telegram / Slack / Discord / WhatsApp 等入口
- 要强调移动端、语音、Canvas 等交互体验
- 要做平台化、长期在线、入口丰富的产品

### 最终建议（一句话）

对 AI 辅助 Linux 内核 / BSP 开发，优先考虑 Hermes 这类“工程执行型 Agent”；
对多渠道个人 AI 助手平台，优先参考 OpenClaw 这类“平台型 Assistant”。
