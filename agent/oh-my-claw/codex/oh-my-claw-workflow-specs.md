# oh-my-claw Workflow Specs（MVP / Phase 1）

## 1. 文档目标

本文档定义 `oh-my-claw` 在 MVP / Phase 1 中的三个核心 workflow：

- `design-proposal`
- `feature-implementation`
- `bug-fix`

本文档的目标是将 workflow 从“概念”细化为“可实现、可测试、可验收”的规格，包括：

- workflow 触发条件
- 输入与输出
- 标准步骤
- 每一步的职责
- Gate 触发点
- 失败路径
- handoff summary 要求

本文档与以下文档保持一致：

- `oh-my-claw-proposal.md`
- `oh-my-claw-mvp-phases.md`
- `oh-my-claw-mvp-implementation-plan.md`
- `oh-my-claw-architecture.md`

如果后续实现与本文档冲突，应优先修改文档并同步其他设计文档，而不是让实现自行偏离。

---

## 2. Workflow 设计原则

所有 MVP workflow 都必须满足以下原则：

1. **共享统一骨架**：所有 workflow 使用相同的大阶段结构
2. **允许任务差异**：不同 workflow 在每个阶段的重点不同
3. **Gate 优先于自由执行**：workflow 必须接受 Entry/Edit/Verify/Exit Gate 约束
4. **输出必须结构化**：handoff 不是随意文本，而是结构化 summary
5. **失败必须可解释**：失败不能只是“没做成”，要说明在哪个阶段失败以及下一步建议
6. **Phase 1 只做单链路闭环**：不引入复杂多 agent 编排

---

## 3. 统一 Workflow 骨架

所有 MVP workflow 统一采用以下阶段：

1. `intake`
2. `scan`
3. `plan`
4. `execute`
5. `verify`
6. `handoff`

并允许以下附加状态：

- `blocked`
- `failed`
- `partial`

## 3.1 通用阶段说明

### `intake`

作用：

- 接收任务
- 形成标准化输入
- 关联 explicit command / user intent

产物：

- `TaskIntake`
- 初步任务标签

### `scan`

作用：

- 构建项目上下文
- 收集规则、结构、任务相关文档

产物：

- `ContextSnapshot`
- 项目规则摘要
- 任务相关文档摘要

### `plan`

作用：

- 输出当前 workflow 的执行计划
- 标识关键验证点
- 标识风险和依赖

产物：

- 结构化计划
- 关键检查项

### `execute`

作用：

- 实际完成 workflow 目标

产物：

- 分 workflow 的核心执行结果

### `verify`

作用：

- 检查结果是否达到最低工程标准

产物：

- 验证结果
- 未验证说明
- 风险补充

### `handoff`

作用：

- 统一整理交付结果
- 标记完成/部分完成/失败
- 输出下一步建议

产物：

- `TaskSummary`

---

## 4. Gate 与 Workflow 的关系

## 4.1 Gate 触发时机

### Entry Gate

触发点：

- `intake` 后、`scan` 前
- 或 `scan` 后、`plan` 前（取决于系统实现）

目标：

- 判断是否必须计划
- 判断是否允许跳过 planning

### Edit Gate

触发点：

- `scan` 后、`execute` 前

目标：

- 确认项目上下文是否充足
- 在未来为 safe edit 提供信号

### Verify Gate

触发点：

- `execute` 后、`verify` 前

目标：

- 判断是否必须验证
- 注入验证建议

### Exit Gate

触发点：

- `verify` 后、`handoff` 前

目标：

- 检查 summary 是否完整
- 检查未完成项是否已标识

---

## 5. Workflow 通用状态模型

建议所有 workflow 至少包含以下状态：

- `workflowName`
- `status`
- `currentStep`
- `completedSteps`
- `artifacts`
- `warnings`
- `errors`

### `status` 值建议

- `ready`
- `running`
- `blocked`
- `failed`
- `partial`
- `completed`

### `artifacts` 典型内容

- plan
- context snapshot
- findings
- proposed changes
- verification result
- summary draft

## 6. Workflow 1：`design-proposal`

## 6.1 适用场景

该 workflow 用于：

- 方案设计
- 技术选型
- 差异分析
- 对已有仓库/系统进行增强设计
- 需要输出结构化提案的任务

典型关键词：

- “设计方案”
- “参考 X 对 Y 的优化”
- “评估差异并提出方案”
- “技术路线”
- “怎么做更合理”

## 6.2 触发条件

满足任一条件时优先进入该 workflow：

- 用户显式调用 `/design`
- Decision Engine 判定 intent 为 `design_proposal`
- 任务包含明显的比较、评估、提案、架构设计诉求

## 6.3 输入

### 必需输入

- 用户任务说明
- 当前工作目录

### 可选输入

- 被参考的仓库路径
- 对比仓库路径
- 已有方案文档
- 最近上下文摘要

## 6.4 成功定义

只有同时满足以下条件，才算该 workflow 成功：

- 识别出目标系统与参考系统的关键差异
- 提供结构化方案，而不是泛泛建议
- 明确 MVP/阶段路线图或优先级
- 明确风险、边界和非目标
- 生成完整 handoff summary

## 6.5 阶段规格

### `intake`

目标：

- 明确目标对象、参考对象、输出类型
- 判断是“设计提案”还是“纯问答”

必须产出：

- 任务目标摘要
- 对比对象清单
- 预期交付物类型

失败条件：

- 未能明确参考对象或目标对象
- 用户目标含糊到无法进入设计流程

失败输出：

- 需要补充的信息清单
- 暂不执行的原因

### `scan`

目标：

- 收集目标仓库和参考仓库的关键信息
- 构建上下文摘要

必须产出：

- 目标系统能力摘要
- 参考系统增强点摘要
- 初步差异点列表

推荐读取：

- README
- AGENTS
- docs
- package/build/config 信息

失败条件：

- 无法定位关键文档
- 缺少足以支撑对比分析的信息

### `plan`

目标：

- 确定设计提案的分析顺序与输出结构

必须产出：

- 对比维度列表
- 方案文档大纲
- 优先级原则

最小计划结构建议：

- 现状盘点
- 差异识别
- 方案定义
- MVP 建议
- 路线图
- 风险与边界

### `execute`

目标：

- 完成对比分析和方案生成

必须产出：

- 现状判断
- 缺口矩阵
- 方案模块划分
- MVP 范围建议
- 分阶段实施建议

禁止行为：

- 只做功能罗列，不形成主线
- 只做理想化设计，不给出落地顺序

### `verify`

目标：

- 检查提案是否具备足够工程化质量

必须检查：

- 是否明确已有能力与缺失能力
- 是否给出边界和非目标
- 是否给出优先级和阶段路线
- 是否避免重复造 OpenClaw 平台能力

### `handoff`

必须输出：

- 方案摘要
- 关键差异结论
- MVP 建议
- 风险与取舍
- 下一步建议文档/动作

## 6.6 `design-proposal` summary 结构

建议包含：

- `completed`
  - 完成了哪些调研与分析
- `design`
  - 方案定位
  - 模块划分
  - MVP 范围
- `risks`
  - 架构风险
  - 范围风险
- `nextSteps`
  - 推荐下一份文档
  - 推荐进入的实施阶段

## 6.7 `design-proposal` 失败路径

### 情况 A：信息不足

处理：

- 输出缺失信息清单
- 产出“初步提案，待补充”状态

### 情况 B：目标过大

处理：

- 自动建议拆分阶段
- 标记当前结果为 `partial`

### 情况 C：上下文矛盾

处理：

- 显式指出冲突来源
- 在 summary 中标记假设

## 7. Workflow 2：`feature-implementation`

## 7.1 适用场景

该 workflow 用于：

- 增加功能
- 小到中等规模代码修改
- 文档与实现同步修改
- 按明确需求完成变更

典型关键词：

- “实现”
- “增加功能”
- “补充支持”
- “在当前路径下生成/修改”

## 7.2 触发条件

满足任一条件时优先进入该 workflow：

- 用户显式调用 `/implement`
- Decision Engine 判定 intent 为 `feature_implementation`
- 任务明确要求对现有系统新增能力

## 7.3 输入

### 必需输入

- 用户功能需求
- 当前目录/项目

### 可选输入

- 约束条件
- 指定文件/模块
- 相关 issue / 方案文档

## 7.4 成功定义

只有同时满足以下条件，才算该 workflow 成功：

- 明确了需求与约束
- 有结构化计划
- 有执行结果说明
- 有验证结论或未验证说明
- 有统一 handoff summary

注：在当前对话“暂时不写代码”的约束下，执行结果可以是 **文档产物或实施计划产物**；真实编码阶段则是代码改动。

## 7.5 阶段规格

### `intake`

目标：

- 确认功能目标
- 识别是否需要修改代码、文档、配置或多者组合

必须产出：

- 功能目标摘要
- 影响范围初判
- 是否属于非琐碎任务的判断

### `scan`

目标：

- 找出相关模块、规则、构建/测试方式

必须产出：

- 相关文件/目录清单
- 关键约束清单
- 推荐验证方式

### `plan`

目标：

- 输出最小改动计划

必须产出：

- 步骤列表
- 影响面说明
- 验证点清单

最小计划结构建议：

- 理解现状
- 修改点
- 输出物
- 验证方式
- 风险

### `execute`

目标：

- 完成功能实现或实现级文档交付

在真实代码阶段应产出：

- 修改文件列表
- 关键实现点
- 相关文档更新

在当前非代码阶段可产出：

- 文件级实施计划
- 接口级设计
- 实施文档

### `verify`

目标：

- 确认结果是否与需求一致

必须检查：

- 是否覆盖目标需求
- 是否说明验证方式
- 是否说明未验证部分
- 是否控制改动范围

### `handoff`

必须输出：

- 已完成内容
- 涉及范围
- 验证情况
- 风险与假设
- 下一步建议

## 7.6 `feature-implementation` summary 结构

建议包含：

- `completed`
  - 已产出的实现/文档/计划
- `scope`
  - 涉及模块或文件范围
- `verification`
  - 已验证项
  - 未验证项
- `risks`
  - 范围风险
  - 依赖风险
- `nextSteps`
  - 若未编码，推荐进入编码阶段
  - 若已编码，推荐进一步测试或 review

## 7.7 `feature-implementation` 失败路径

### 情况 A：上下文不足

处理：

- 通过 Edit Gate 阻止直接进入 execute
- 回退到补充扫描或输出阻塞说明

### 情况 B：需求边界不清

处理：

- 输出需求歧义点
- 标记当前为 `blocked`

### 情况 C：任务过大

处理：

- 自动拆分为子阶段
- 将当前结果标为 `partial`

## 8. Workflow 3：`bug-fix`

## 8.1 适用场景

该 workflow 用于：

- bug 修复
- 错误定位
- 回归风险评估
- 失败链路分析

典型关键词：

- “修复 bug”
- “定位问题”
- “为什么失败”
- “错误恢复”
- “异常”

## 8.2 触发条件

满足任一条件时优先进入该 workflow：

- 用户显式调用 `/debug`
- Decision Engine 判定 intent 为 `bug_fix`
- 任务包含错误、异常、失败、修复等高信号描述

## 8.3 输入

### 必需输入

- 问题描述
- 当前项目上下文

### 可选输入

- 报错信息
- 日志
- 失败测试
- 可复现步骤

## 8.4 成功定义

只有同时满足以下条件，才算该 workflow 成功：

- 明确症状
- 给出根因判断或至少根因假设
- 给出修复建议/修复方案
- 给出回归验证建议
- 形成结构化 handoff summary

## 8.5 阶段规格

### `intake`

目标：

- 识别这是症状描述、错误日志、失败任务还是复现请求

必须产出：

- 症状摘要
- 问题影响范围初判
- 是否具备复现信息

### `scan`

目标：

- 找到与错误相关的模块、配置、规则、日志来源

必须产出：

- 相关文件与模块
- 相关规则与环境约束
- 可用的诊断证据列表

### `plan`

目标：

- 输出 root-cause-first 的排查路径

必须产出：

- 排查顺序
- 优先假设
- 验证方法
- 修复策略方向

最小计划结构建议：

- 识别症状
- 收集证据
- 缩小范围
- 提出根因
- 修复/规避
- 回归验证

### `execute`

目标：

- 形成根因分析和修复结果

在真实代码阶段应产出：

- 根因说明
- 修复改动
- 相关回归点

在当前非代码阶段可产出：

- 排障分析报告
- 修复计划
- 风险说明

### `verify`

目标：

- 判断是否完成最小回归验证要求

必须检查：

- 是否说明根因证据
- 是否说明修复是否验证
- 是否说明剩余风险

### `handoff`

必须输出：

- 症状
- 根因
- 修复结果/修复方案
- 验证情况
- 剩余风险
- 下一步建议

## 8.6 `bug-fix` summary 结构

建议包含：

- `issue`
  - 症状描述
- `rootCause`
  - 根因或根因假设
- `fix`
  - 修复动作或建议
- `verification`
  - 已验证 / 未验证
- `risks`
  - 回归风险 / 未确认点
- `nextSteps`
  - 继续验证 / 继续修复 / 观察项

## 8.7 `bug-fix` 失败路径

### 情况 A：无法复现

处理：

- 输出缺失证据
- 给出最小补充材料要求

### 情况 B：根因不唯一

处理：

- 输出候选根因列表
- 按优先级排序
- 标记结果为 `partial`

### 情况 C：无法验证修复

处理：

- 明确未验证原因
- 输出建议验证方案

---

## 9. 三个 Workflow 的差异矩阵

| 维度 | design-proposal | feature-implementation | bug-fix |
|------|-----------------|------------------------|---------|
| 主要目标 | 输出方案 | 输出实现结果/实施产物 | 输出根因与修复 |
| 核心风险 | 方案空泛、无边界 | 范围失控、验证不足 | 根因误判、回归不足 |
| `scan` 重点 | 对比与架构信息 | 相关模块与约束 | 日志、错误、相关模块 |
| `plan` 重点 | 对比维度与方案结构 | 最小改动计划 | root-cause-first 排查路径 |
| `execute` 重点 | 方案生成 | 实现或实施计划 | 修复或修复计划 |
| `verify` 重点 | 方案是否成体系 | 是否满足需求与验证 | 是否支持根因与修复结论 |
| handoff 核心 | 定位、模块、路线图 | 完成项、范围、验证 | 症状、根因、修复、风险 |

## 10. 通用失败与降级策略

所有 workflow 都应支持以下通用状态：

## 10.1 `blocked`

表示：

- 缺少必要输入
- 缺少关键上下文
- 缺少执行前提

输出要求：

- 阻塞原因
- 需要补充的信息
- 建议下一步

## 10.2 `partial`

表示：

- 已完成部分工作
- 但尚未形成完整闭环

输出要求：

- 已完成部分
- 未完成部分
- 风险
- 下一步建议

## 10.3 `failed`

表示：

- 当前 workflow 无法继续
- 且不能形成有价值的中间结果

输出要求：

- 失败阶段
- 失败原因
- 重试建议或替代 workflow 建议

---

## 11. Workflow 测试建议

## 11.1 模板级测试

每个 workflow 至少需要：

- 正常路径测试
- 缺少输入测试
- Gate 阻断测试
- partial 输出测试
- summary 结构测试

## 11.2 场景级测试

### `design-proposal`
- 比较两个仓库并生成方案
- 仅有目标仓库、缺少参考仓库
- 范围过大的方案请求

### `feature-implementation`
- 小功能请求
- 需求模糊请求
- 非琐碎任务要求直接执行

### `bug-fix`
- 带错误描述的 bug
- 仅说“有 bug”但不给证据
- 根因不唯一的复杂问题

## 11.3 验收重点

- workflow 是否走完统一骨架
- Gate 是否在正确阶段触发
- 输出是否满足各自 summary 结构
- 失败路径是否仍能提供有价值输出

---

## 12. Workflow 规格结论

MVP / Phase 1 的三个 workflow 不是三个彼此独立的小功能，而是：

> **在统一主链路和统一骨架之下，针对三类高频 coding task 的三种受控执行模式。**

因此，实现时必须坚持：

- 同一套状态模型
- 同一套 Gate 机制
- 同一套 handoff 框架
- 不同 workflow 只改变任务重点，不改变系统主链路

这能保证：

- 架构清晰
- 测试可复用
- 文档可统一
- 后续 continuity / safe edit / doctor 更容易接入
